Flight plan before takeoff

Spec, design and plan: three documents that turn a wish into steps an AI can execute and a stranger can check.

Pilots file a plan before they fly

No pilot takes off and "sees where it goes." They file where they are landing, which aircraft they are flying, and the checkpoints on the way. Air traffic control can then tell, at any moment, whether the flight is on course.

Steps 2 and 3 of the lab are that filing. Three documents, three questions:

📐

docs/spec.md

The destination. Exactly what the brief looks like, field by field, quoted from the example PDFs.

🧩

docs/design.md

The aircraft. Which part owns which job, and what each part must never do.

🗺️

docs/plan.md

The checkpoints. Ordered steps, exact files, one proof command per step.

⚖️

docs/decisions/

The logbook. One ADR per real decision, so nobody re-argues it next month.

The spec: every field needs a quote

The spec's heart is the contract, a table that pins down each piece of data the brief contains. The key column is the last one: every rule must be backed by real words from the reference PDFs.

docs/spec.md 
## The contract

| Field | Type | Rule | Example from the reference |
| --- | --- | --- | --- |
| `TEMPLATE` | `TEMPLATE` | `TEMPLATE — imperative, max nine words, names the artifact` | `TEMPLATE — quoted from the PDF` |
PLAIN ENGLISH

The contract: the agreed shape of a brief.

 

For each field: its name, its type, the rule it obeys, and a real example.

(Table divider.)

One example rule style: "imperative, max nine words, names the artifact." Precise enough that a test can check it. The example must be quoted, not invented.

Step 2 then works test-first: test/schema.test.ts is written and fails, and only then does src/brief.ts get written to make it pass. SOLO.md even asks you to check that "git log show[s] the test commit before brief.ts."

The design: boundaries become code

The design template has a section that is easy to skim past and is the most important one. It asks how each rule from intent.md is enforced by the program itself, not by asking the AI nicely.

docs/design.md 
## Boundaries in code

- Bound the task: `TEMPLATE — which options remove capability from the model.`
- Watch the loop: `TEMPLATE — which options cap and log the run.`
- Interrupt on purpose: `TEMPLATE — where the human sits, and why not inside the run.`

## Hooks (deterministic, hold without asking)

- `TEMPLATE — the rule from the prompt that must hold even if the model ignores the prompt, and the code that holds it.`
PLAIN ENGLISH

How the fence from intent.md is built into the software.

 

Take abilities away: the model simply is not given a shell or a write tool, so it cannot misuse one.

Put a limit on how many steps the agent loop can take, and log every tool call.

The human reviews after the run, not in the middle. A 3 a.m. scheduled job cannot wait for someone to click "allow."

 

Hooks: rules enforced by plain code, every time.

If a rule matters, do not trust the prompt alone. Write code that holds it even if the model ignores the instructions.

💡
A prompt is a request. Code is a lock.

"Please don't write anything" in a prompt usually works. Not handing the model a write tool always works. When a rule really matters, ask your AI assistant to remove the capability, not to add a sentence to the prompt.

The plan: checkpoints you can actually run

The plan's step table has a Proof command column. Those commands are real; they live in package.json, the one piece of real configuration on main.

package.json 
  "scripts": {
    "brief": "tsx src/main.ts",
    "brief:sample": "tsx src/main.ts --sample",
    "typecheck": "tsc --noEmit",
    "test": "tsx --test test/*.test.ts"
  },
PLAIN ENGLISH

Named shortcuts. Typing npm run <name> runs the command next to it. (npm is the tool that reads this file.)

The real run: start the program in src/main.ts using tsx, reading live sources.

The safe run: same program with a flag that swaps in sample data. No tokens needed.

Check that every value matches its declared type, without producing any output files.

Run every file in test/ ending in .test.ts.

End of the shortcuts.
