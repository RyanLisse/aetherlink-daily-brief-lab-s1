The SOLO loop

Walking all seven steps on your own, catching up when stuck, and why the route ends where it began.

A trail with numbered markers

A good hiking trail has numbered markers, and at each one a map showing exactly where you should be. Lost? Walk to the next marker and carry on from there.

SOLO.md is that trail for one person with their own GitHub, Linear and Notion. The markers are Git tags: step-1-intent through step-7-gate-deploy, each pointing at the reference solution after that step.

1
Plan: intent (15 min)

Claude Code interviews you one question at a time. You cut.

2
Plan: spec and contract, test first (25 min)

Quote the PDFs, write the failing test, then the code.

3
Design: one decision, a plan with proof (15 min)

Claude Code in plan mode: read-only until you accept.

4
Build: render the sample (25 min)

The first artifact: out/latest.html, no API key needed.

5
Build: the loop and one read-only tool (20 min + live run)

Take the reference files on purpose, then add one tool yourself.

6
Test: record the evidence (15 min)

Three commands, exit codes, one screenshot, one reviewer.

7
Deploy: the gate and the schedule (15 min)

Decide the gate, then run the brief every weekday morning.

The three commands you will use all day

SOLO.md 
git diff main step-2-spec --stat              # what a step adds
git diff step-2-spec -- docs/spec.md          # your file against the reference
git checkout step-5-build-agent -- src/sources.ts   # take one reference file
PLAIN ENGLISH

Peek at the map. List which files the reference solution changed between empty main and the end of step 2, with a count of lines per file. (git diff.)

Compare your work. Show, line by line, how your spec differs from the reference spec.

Catch up. Copy just one file from the step 5 reference into your branch, leaving everything else as you wrote it. (git checkout.)

🧭
Catching up is part of the design

Step 5 opens with "this is the deliberate catch-up": you are told to take the reference sources.ts and agent.ts, then read them. Reading good code and adding one piece yourself teaches more than fighting an SDK for two hours.

The live run: read the log, not just the page

Step 5 ends with the first real run, using your read-only tokens from .env.

SOLO.md 
set -a && . ./.env && set +a
npm run brief 2> run.log

Read `run.log`: the `mcp=[…]` line names the connected sources, every `→`
line is a tool call. Then read `out/latest.html`.
PLAIN ENGLISH

Load every setting in .env (your tokens) as environment variables for this terminal session.

Run the real brief, and send its diagnostic output (2>, the error stream) into a file called run.log.

 

In the log, one line lists which sources connected over MCP, and each arrow line is one tool call.

Only after reading the log, read the brief itself.

The check that follows is the sharpest in the lab: "is every sentence in the brief traceable to a tool call in run.log?" A sentence with no matching tool call came from nowhere.

Where the trail ends: back at the start

SOLO.md 
## When you are done

Seven files a stranger can point at, one brief you did not write, and a gate
you decided. Tomorrow's run reads what you merged today; when a footnote in
the brief changes `intent.md`, the loop has closed.
PLAIN ENGLISH

What "finished" looks like.

 

Artifacts anyone can inspect, a brief written by the agent, and a human decision on record.

Tomorrow the scheduled run uses what you merged today. And when something the brief reports teaches you that your intent was wrong...

...you go back and change intent.md. The route is a circle, not a line.

💡
Documents are living, not paperwork

AGENTS.md rule 6: "when evidence changes the intent, the spec or the plan, go back and change that document before continuing." If your AI assistant patches code to match a surprise without updating the document above it, the documents stop being true, and the next session reads a lie.
